# M2 external applicant API

Academy websites submit prospects as applications. They do not create active student/player profiles. Owner/Admin users manage credentials at `/app/settings/api`; secret values are shown once, stored only as SHA-256 hashes, individually revocable and tenant scoped.

## Authentication and limits

Send the credential from the website's server, never public browser JavaScript:

```http
Authorization: Bearer aca_...
Accept: application/json
```

Version 1 endpoints are limited to 60 requests per minute per client by the application throttle:

- `GET /api/v1/configuration` — active programmes, branches, countries, terminology and custom-field definitions.
- `POST /api/v1/applications` — submit an application.
- `GET /api/v1/applications/status?external_reference=...` — retrieve the application reference and lifecycle status.

## Submission contract

The application endpoint accepts the same standard applicant, guardian, programme, branch and `custom_fields` values as the academy UI. It additionally requires:

- `external_reference`: a unique stable ID generated by the source website;
- `consent_accepted`: an accepted boolean value;
- `privacy_policy_version`: the version displayed when consent was collected.

The first valid request returns `201`. Repeating the identical payload with the same external reference is idempotent and returns the existing application with `200`. Reusing that reference with changed data returns `409`. Matching name plus date of birth, or name plus guardian phone, is also rejected as a probable duplicate. Programme, branch and custom-field IDs/keys are always validated inside the API key's academy.

The API stores `source=api`, consent time, policy version and a canonical submission hash. API key use and application creation are auditable. Applications appear in the normal admissions screen with their external reference and consent indicator.

## Payment boundary

The API intentionally ignores any client-supplied claim that payment succeeded. Enrollment may only follow a server-verified academy payment recorded in the academy finance ledger. Online academy payment collection is pending the required merchant-model decision: direct academy Paystack accounts versus platform-mediated collection. SaaS subscription billing remains separate in all cases.
